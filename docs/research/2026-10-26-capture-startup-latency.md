# 截图快捷键到选区就绪：窗口关闭等待修复

用户反馈截图快捷键按下后，需要较久才能开始选区。本轮定位并修复了截图窗口重建时的一条约 2 秒阻塞路径。

## 已有运行证据

读取本机应用数据库中的性能日志，仅检查计时信息：

- 2026-10-22：冻结截图会话耗时 73.1 ms；准备窗口阶段耗时 661.8 ms；打开窗口阶段耗时 2006.4 ms；总计 2675.8 ms，随后报 `Timed out waiting for previous capture window to close`。
- 2026-10-24：另一次冻结截图会话耗时 45.5 ms，随后也出现旧窗口关闭超时。
- 成功复用窗口的历史记录中，打开窗口之前的后端总耗时约 48–99 ms。这些记录不包含最终前端解码和显示，不代表完整端到端延迟。

## 原因

原来的 `prepare_capture_window` 和 `open_capture_window_for_session` 都在原生主线程执行。在需要重建窗口时，它们调用 `window.destroy()`，随后用 `thread::sleep` 同步轮询，等待窗口标签从 Tauri 的窗口表移除。

销毁和标签释放需要原生事件循环继续处理。同步轮询占住主线程，恰好阻止了自己等待的关闭流程，最终触发 2 秒超时。

## 修复

原生窗口操作返回“就绪”或“关闭中”。运行时收到“关闭中”后退出主线程回调，在异步任务中等待标签释放，再将下一步窗口创建派发到主线程。等待采用异步计时器。

保留了真实异常的 2 秒超时上限、当前 Space 上的窗口复用策略、原有几何配置和冻结屏幕像素的要求。

## 回归测试

```sh
cd src-tauri
cargo test --lib closing_capture_window_allows_queued_destruction_to_run -- --nocapture
```

测试调用生产代码的标签释放等待函数，在单线程执行器上排队一个销毁操作，模拟事件循环需要继续执行才能释放窗口的行为。

- 修复前：连续两次失败，分别阻塞 2.0116 s 和 2.0052 s，出现相同关闭超时。
- 修复后：通过，测试运行约 0.02 s；断言排队销毁可以执行且此步骤在 250 ms 内完成。

其他验证：`cargo test --lib` 为 570 项通过、1 项已有的手动 WindowServer 探针跳过；`cargo fmt --all -- --check` 和 `npm run build` 通过。前端原有基线为 956 项测试通过，本修复未更改生产前端代码。

## 测量范围

上述改进数值仅描述窗口关闭等待的回归测试。尚未测量新构建从真实快捷键到选区显示的完整耗时，也未完成多显示器和全屏 Space 的原生体验验收。本轮修改位于工作区，没有替换 `/Applications/SnapLingo.app`，需要使用新构建才能生效。

这类问题应以“事件循环仍能推进”的回归测试约束；仅检查超时常量大小无法发现主线程被阻塞。
